# Forge deployment: Vercel, Render, and a Docker worker host

This deployment uses Vercel for the Next.js frontend, Render for the FastAPI API and managed PostgreSQL/Key Value services, and a separate Linux VM for the Docker execution worker. The current `main` code uses bearer tokens from the OAuth redirect, so the frontend and API do not need to share a cookie domain. Keep exact HTTPS origins configured for CORS.

## Vercel frontend

1. Import `Surya270106/Forge` from GitHub. Set **Root Directory** to `apps/frontend` and choose the Next.js framework preset.
2. Set Node.js to `24.x`, install command to `npm ci`, build command to `npm run build`, and leave Next.js output at its default. The frontend has its own `package-lock.json`.
3. Set Production environment variables:
   - `NEXT_PUBLIC_API_BASE_URL=https://<render-api-host>`
   - `NEXT_PUBLIC_EVENT_URL=wss://<render-api-host>`
   - `STRICT_PROD=true`
4. Redeploy after changing either public URL; Next.js embeds these values during the build. Use the actual Vercel frontend origin as Render's `FRONTEND_URL` and in `CORS_ORIGINS`.

The first Vercel deployment can be created before the API exists. Its OAuth and API calls will not work until the real Render URL is configured and Vercel is redeployed.

## Render services and environment

The root `render.yaml` defines:

- `forge-api`: Docker web service built from `docker/Dockerfile.api` with repository-root context, `/ready` health checks, and Alembic migrations before each deploy.
- `forge-postgres`: PostgreSQL 16 in Oregon with a 15 GB disk.
- `forge-redis`: authenticated Render Key Value in Oregon with journal and snapshot persistence.

Create or sync the Blueprint after connecting the GitHub repository. `REDIS_URL`, `FRONTEND_URL`, `CORS_ORIGINS`, and GitHub credentials are prompted as unsynchronized values. Enable Key Value internal authentication in the Render Dashboard and use the authenticated internal connection URL. Keep both datastore external IP allow lists empty until the worker VM is ready.

Set the following on the Render API service:

| Variable | Value |
| --- | --- |
| `ENVIRONMENT` | `production` (set by the Blueprint) |
| `DATABASE_URL` | Render's private PostgreSQL connection string (set by the Blueprint) |
| `REDIS_URL` | Authenticated internal Key Value connection string |
| `FRONTEND_URL` | Exact frontend origin, such as `https://forge-ui.vercel.app` |
| `CORS_ORIGINS` | JSON array containing that exact origin, such as `["https://forge-ui.vercel.app"]` |
| `SECRET_KEY` | Generated by the Blueprint; keep stable |
| `ENCRYPTION_KEY` | Generated by the Blueprint; keep stable so stored credentials remain decryptable |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | GitHub OAuth App credentials |
| `GITHUB_WEBHOOK_SECRET` | Random secret matching the GitHub webhook configuration |
| `SANDBOX_IMAGES` | JSON list set by the Blueprint; keep the configured values unless you build compatible images |

The current `main` migration set and API use the same PostgreSQL account. Do not assume the separate `forge_app`/`forge_outbox` role setup from the earlier deployment branch; that role model is not present on current `main`. Keep the Render database credentials private and review least-privilege role support before treating the service as production-hardened.

Render's pre-deploy migration runs `/app/.venv/bin/alembic upgrade head` against `DATABASE_URL`; it applies migrations without resetting the database. This requires a paid Render web service plan. Back up the database before major schema changes.

## OAuth and webhook setup

Set the GitHub OAuth App callback URL to:

`https://<render-api-host>/api/v1/auth/github/callback`

Set its homepage URL to the Vercel frontend. The current frontend receives a bearer token through the OAuth redirect and sends authenticated API requests cross-origin; set `CORS_ORIGINS` to the exact Vercel origin, without a path or wildcard. Configure repository webhooks with the API route shown by the application's GitHub webhook endpoint and the same `GITHUB_WEBHOOK_SECRET` value.

## Separate Docker execution worker

Render does not provide the host Docker Engine socket needed by `DockerSandbox`. The Blueprint therefore does not run a worker. Use a dedicated Linux VM with Docker Engine, a protected workspace directory, and the repository's `docker-compose.worker.yml` / `docker/Dockerfile.worker`.

1. Create `/srv/forge/workspaces` on the VM and make it writable by the worker container's `forge` user (UID 1000). Keep this path identical inside the worker container and on the VM so child containers can bind-mount it.
2. Create an ignored `.env.worker` file beside the compose file with the same `DATABASE_URL`, `REDIS_URL`, `FRONTEND_URL`, GitHub credentials, `SECRET_KEY`, `ENCRYPTION_KEY`, and `SANDBOX_IMAGES` as the API. For the worker, use Render's external PostgreSQL and Key Value URLs, and allow the VM's stable egress IP in both datastore IP allow lists. Do not allow `0.0.0.0/0`.
3. Set `DOCKER_GID` in the VM's ignored `.env` to the numeric group ID that owns `/var/run/docker.sock` (`stat -c '%g' /var/run/docker.sock`). Start the worker with `docker compose -f docker-compose.worker.yml up -d --build`.
4. Confirm the worker connects to PostgreSQL and Key Value and consumes queued jobs. Keep the Docker socket local to this dedicated host; never expose an unauthenticated Docker TCP endpoint.

Execution sandboxes default to Docker's `none` network. Keep the worker VM patched and dedicated because access to its Docker socket grants control over that host. The API's filesystem is ephemeral; workspace data needed by jobs must remain on the worker's mounted persistent path.

## Deployment and verification order

1. Push the reviewed deployment changes to GitHub `main` and connect the Vercel project and Render Blueprint to that repository/branch.
2. Create the Vercel project, note its production origin, and set `apps/frontend` as its root.
3. Create/sync Render PostgreSQL, Key Value, and API services. Supply the exact Vercel origin, CORS JSON, authenticated Redis URL, and GitHub credentials/secrets.
4. Wait for Render `/ready` to pass and verify the API has HTTPS. Set the real API HTTPS/WSS URLs and `STRICT_PROD=true` in Vercel Production variables, then redeploy.
5. Set the GitHub OAuth callback and webhook URL/secret. Verify sign-in, authenticated API calls, and WebSocket connection from the deployed frontend.
6. Build the sandbox images and deploy the worker VM. Verify a test repository import and execution before enabling user workloads.

A healthy API and frontend do not establish that repository execution is working. The Docker worker must be online and tested separately.
