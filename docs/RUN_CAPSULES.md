# Forge Run Capsules

## Scope and design

Run Capsules are immutable, versioned snapshots of an execution's **recorded** evidence. They reuse execution jobs, lease generations, prepared patches, Context Lens change sets, Verification Intelligence decisions, Safety Gate snapshots, verification results, and Flight Recorder events. They neither execute work nor decide whether a patch may be approved or published. Existing digest-bound approval, tenant authorization, PostgreSQL RLS, the outbox, and the Docker sandbox remain the enforcement boundaries.

The implementation writes a snapshot in the same PostgreSQL transaction as `execution.started`, `worker.lease_expired`, terminal execution events, and terminal verification events. The event ID is the unique idempotency key. A later transition creates another row; it never edits an earlier snapshot. `PARTIAL` means the execution or verification record was still incomplete at capture. `FINAL` means the particular terminal transition was recorded, **not** that every possible external fact was captured or that the run succeeded. A completed execution awaiting verification is partial. Failed and cancelled executions get a final snapshot with their actual failure state. Verification retries or a later patch digest must create new evidence rather than rewriting a prior row.

The new migration `a4d1e8c2b930` follows Verification Intelligence head `f2c7d4e9a110`. It adds `run_capsules` and `run_capsule_artifacts`, a scoped execution foreign key, unique event association, artifact size checks, forced tenant RLS, and append-only triggers. Apply this migration **before** starting updated API or worker processes. Existing data is retained. Older runs are not backfilled and the API shows their missing capsule explicitly.

## Manifest and sources

The canonical UTF-8 JSON manifest has `schema_version: 1`, capsule state, organization/workspace/repository/execution IDs, lease attempt, exact stored base commit, the triggering event ID and sequence, execution/verification states and timestamps, patch ID/digest, Context Lens change-set ID, Verification Intelligence plan ID, SHA-256 of the stored Safety Gate policy snapshot, bounded verification command outcomes, bounded Flight Recorder event IDs, runtime/provider/model metadata when present, sandbox image reference and Docker image ID when recorded, artifact inventory, provenance names, and `missing_evidence` reason codes. Workspace ID is the organization ID in Forge's current workspace model.

The base revision comes from `execution_jobs.commit_sha_before`; it is not inferred from today's repository checkout. Patch digest and change set are separate recorded facts. Verification results report command status and exit code, not individual test-case success or coverage. Model/provider metadata comes from an allowlisted Flight Recorder event, and Forge's application version comes from installed package metadata. A container image ID is captured with a bounded Docker inspect after container creation when available; a tag alone is mutable. The full agent code revision, resolved external package set, model response determinism, and host state are not currently captured and must not be inferred.

At most the most recent 100 Flight Recorder event references and 40 verification command results enter one manifest. `missing_evidence` marks truncation and absent patch, change set, selection plan, policy, model metadata, runtime version, sandbox image or image ID; it always marks the unavailable Forge source release revision. A selected plan carries its own patch digest, and a mismatch with the captured change set is explicit. A capsule's SHA-256 is calculated from sorted-key compact JSON and checked on read/export. This catches accidental corruption; it is not a signature against an administrator who can rewrite the database and recompute the hash.

## Artifacts and privacy

Artifacts are two small JSON documents derived from trusted database fields: an execution state summary and a verification-result summary. Operators may lower the per-document limit with `CAPSULE_ARTIFACT_MAX_BYTES` (1–16384, default 16384) and the document count with `CAPSULE_ARTIFACT_MAX_COUNT` (0–2, default 2). Oversized or excess material is omitted with a missing-evidence reason. Artifact rows have content hash, byte length, scoped capsule foreign key, tenant RLS, and append-only protection. The retrieval API rechecks the stored bytes against both the row and manifest inventory. Artifact IDs are opaque UUIDs. No caller supplies a filesystem path, so traversal and symlink escape are outside this adapter's input surface. PostgreSQL is the shared store; there is no worker-local artifact path or cross-host filesystem requirement for these structured documents.

The feature does **not** automatically retain raw stdout/stderr, source files, diffs, prompts, OAuth credentials, tokens, environment dumps, or whole workspaces. Existing verification log access remains governed by its current API and retention rules; it is not copied into a capsule. Extending artifacts to arbitrary files would need a dedicated allowlist, redaction, per-tenant quota and encryption policy, content scanning, and shared object storage. The current two-document adapter avoids an unnecessary file service. There is no automatic pruning: rows and artifacts are retained with Flight Recorder evidence indefinitely until an explicit reviewed retention policy exists. Monitor PostgreSQL growth and backups.

## Inspection API and workspace

All routes require the existing authenticated `exec:read` permission and match the execution, repository and active organization. Cross-tenant and cross-execution IDs return 404. The API checks manifest and artifact hashes before returning content.

| Route | Result |
| --- | --- |
| `GET /api/v1/executions/{id}/capsules` | Latest 20 snapshots with truncation flag. |
| `GET /api/v1/executions/{id}/capsules/{capsule_id}` | One verified manifest. |
| `GET /api/v1/executions/{id}/capsules/{capsule_id}/export` | Canonical versioned JSON bytes; no dynamic timestamps added. |
| `GET /api/v1/executions/{id}/capsules/{capsule_id}/artifacts/{artifact_id}` | One authorized, hash-checked structured artifact. |

The task workspace's Context tab adds a Run Capsules section showing identity, status, base revision, patch digest, runtime and image facts, verification outcomes, missing evidence, and artifact inventory. It links engineers to the existing Context Lens and Flight Recorder views for detailed evidence. Download actions use the same authenticated headers; they do not trigger replay, model calls or publication.

## Recovery and reproducibility limits

Capsule rows and artifacts are inserted in the same transaction as the triggering Flight Recorder event. A transaction rollback leaves neither a capsule nor its artifact inventory. Retried event delivery returns the prior event and cannot duplicate its capsule. Lease expiry creates a partial interruption snapshot; a later recovery or terminal transition adds its own snapshot. No final row is mutated on a later verification retry or patch change. A missing or failed capture is visible as no capsule for that event; it must not be interpreted as successful execution.

The manifest supports deterministic **inspection** of captured facts. It does not guarantee deterministic **replay**. Source repositories or package registries may change, image tags can move, external services and model responses can vary, and the worker host or sandbox may be unavailable. A future replay action requires a separate permission, a new execution and lease, Safety Gate review, isolated workspace, pinned dependencies and image, and an explicit decision about external effects. No current capsule endpoint reruns commands, contacts providers, publishes to GitHub, or restores a filesystem.

## Local validation and deployment

Use an isolated migrated PostgreSQL database and Redis for integration; never point test commands at production. The Docker worker requires a Docker-capable host and a shared repository workspace; Vercel and an ordinary Render web service cannot run it. Frontend/API/worker must use compatible code and the same PostgreSQL schema. No hosted or signed-in browser flow is established by the local tests. Report real worker results separately from mocked selection tests and synthetic Bench fixtures.

On 14 November 2026, the locked backend suite had **200 passed, 76 skipped, 22 warnings** without optional infrastructure. The focused capsule, Flight Recorder and Verification Intelligence PostgreSQL suite had **10 passed, 27 warnings**. Those warnings were Pydantic schema deprecations, an `httpx`/Starlette test-client deprecation, and deliberately short JWT fixture keys; they did not change assertions. An isolated real PostgreSQL → Redis/outbox → Docker worker run passed its five execution/verification scenarios, including passing and failing checks. A second real worker case with a synthetic published Atlas base snapshot ran the selected pytest verifier, recorded an unrelated verifier as `SKIPPED`, and wrote a final capsule matching the selection plan and patch digest. Each worker test reported four existing Pydantic deprecation warnings. The Docker sandbox regression set had **11 passed**. These worker cases use fixture repositories and a local pytest sandbox image, not a live model or hosted worker.

Fresh Alembic upgrade reached the single head `a4d1e8c2b930` and `alembic check` found no pending operations. A seeded database upgraded from `f2c7d4e9a110` and retained its patch and execution/repository/organization relationships. Focused Ruff and Pyright passed. Frontend lint, TypeScript check and production build passed; local API, worker and frontend images built; `docker compose config --quiet` passed. No real signed-in browser/OAuth journey was run.

Dependency audit is a **separate release blocker**. `npm audit` on the unchanged frontend lockfile reported six moderate development-tool advisories in five `@typescript-eslint` packages and `minimatch`; `npm audit --omit=dev` reported zero production advisories. A pinned production Python export from the unchanged `uv.lock` produced 46 pip-audit vulnerability records across `aiohttp`, `certifi`, `cryptography`, `filelock`, `litellm`, `multidict`, `PyJWT`, and `urllib3`. Pip-audit did not supply a severity classification in this summary, and records may include multiple advisories per package. Review current advisories and compatible patched versions in a dedicated dependency change, then rerun the entire release gate before hosted deployment. Run Capsules changed no dependency manifest or lockfile.
