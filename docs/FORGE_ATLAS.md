# Forge Atlas

Atlas builds an evidence-backed graph for a repository checkout or a pinned Git commit. It reuses Forge's Tree-sitter registry, repository workspace, PostgreSQL tenant model, transactional outbox, Redis repository stream, and worker. The older repository-memory index stays available to its existing callers. Atlas is advisory: it cannot grant execution capabilities or replace verification and Safety Gate checks.

## Data and lifecycle

Migrations `c4b7a9e1d620` and `d6a1f8b2c340` add `atlas_jobs`, `atlas_snapshots`, `atlas_file_facts`, `atlas_nodes`, and `atlas_edges`, then an optional execution link. All Atlas rows are organization and repository scoped; the migrations apply forced PostgreSQL RLS, foreign keys, and indexes. Published snapshots and their graph rows cannot be changed or deleted. A snapshot records the Git commit and tree, a fingerprint of indexed content, dirty-workspace status, parser/indexer/config versions, counts, and bounded warnings. A dirty checkout retains its HEAD commit only as context; its source fingerprint is the actual indexed identity.

`POST /index` creates an idempotent `QUEUED` job and an outbox event. The repository worker claims it with a lease, scans outside the database transaction, rechecks a mutable checkout for changes, and publishes graph rows and the `SUCCEEDED` status in one transaction. A failed job leaves earlier published snapshots available. Duplicate queue deliveries cannot republish a completed job. The stale-job sweeper requeues expired leases up to three attempts. Lifecycle events (`index_requested`, `index_started`, `snapshot_published`, `index_failed`) go through the transactional outbox. With a validated same-organization, same-repository `execution_id`, actual request, start, parsed-file, publication, and failure transitions also enter that execution's Flight Recorder. Repository-only jobs have no execution ID and cannot appear in an execution-scoped trace.

Unchanged file facts are reused from a compatible published snapshot when their checksum and parser version match. Edges are resolved afresh against the complete new file set, so removed or changed declarations cannot leave stale relationships. Published historical snapshots remain separate.

## Graph semantics

Test files include Python `test_*` paths, `tests/` and `__tests__/` directories, and JavaScript/TypeScript `.test.*` or `.spec.*` filenames.

Supported source languages are Python, JavaScript, TypeScript, and TSX. Atlas extracts repository, revision, file, module, directory-package, class, function, method, interface, test file, and test case nodes. A directory-package is a path grouping, not proof of an installed package. It records containment, definitions, local imports, direct calls, simple class/interface inheritance, and import-based test associations. Each relationship includes a source file and line, method, resolution (`RESOLVED_STATIC`, `INFERRED`, or `UNRESOLVED`), and confidence (`HIGH`, `MEDIUM`, or `LOW`). A test import is an inferred association, never proof of coverage. Unknown imports, ambiguous calls, and complex base expressions stay unresolved or are omitted. Atlas does not yet resolve package aliases, re-exports, dynamic dispatch, arbitrary references, or external package versions; consumers must not treat those edges as known.

The scanner skips symlinks, protected credential paths, binary and malformed files, common build and dependency directories, and files above 1 MiB. It caps parsed files, candidate files, aggregate bytes, graph rows, and the wait for each scan. Python's thread timeout cannot forcibly stop an already running parser; a process-isolated parser is needed before indexing hostile repositories at high volume. It stores identifiers, hashes, and line evidence, not source bodies. Production indexing should use the Linux worker: the Windows file-open fallback cannot provide the same descriptor-level symlink protection for a concurrently changing untrusted checkout. Git revision indexing reads blobs without executing repository code. No indexing path installs dependencies or imports target modules.

The job API exposes queue/running/terminal status, attempts, and a sanitized error code. There is no intermediate per-file progress or user cancellation for Atlas indexing yet. Source lines are derived from Tree-sitter byte offsets: the parser's point accessor crashed on one larger Forge Python file in local testing, and the regression test retains that file as a fixture.

Import module labels that resemble credentials and complex call expressions are redacted before file facts are persisted. A dynamic call remains unresolved with the label `<dynamic>`; Atlas never stores its source expression.

Impact analysis traverses reverse resolved `IMPORTS`, `CALLS`, `TESTS`, `EXTENDS`, and `IMPLEMENTS` edges with a maximum depth of five, 200 results, cycle detection, confidence filtering, and evidence chains. Unresolved edges are shown separately. The SQL query fetches bounded frontiers rather than loading a whole graph. Snapshot comparison accepts at most 10,000 nodes and 30,000 edges per side, reports unique checksum-backed file renames, returns at most 500 items per change category with exact totals and a `truncated` flag, and rejects incompatible parser versions. Ambiguous same-content moves remain added/removed files rather than guessed renames. Larger comparisons need an offline workflow. Graph and symbol listings are paginated.

## API and UI

All routes are under `/api/v1/repositories/{repository_id}/atlas`. `POST /index` requires repository import permission and a UUID idempotency key, with an optional full commit SHA and validated execution ID. `GET /jobs/{job_id}`, `/snapshots`, `/snapshots/{snapshot_id}`, `/graph?snapshot_id=…`, `/symbols?snapshot_id=…&query=…`, `/impact?snapshot_id=…&node_key=…`, `/tests?snapshot_id=…&node_key=…`, `/diff?left=…&right=…`, and `/nodes/{node_id}` require repository read permission. The server verifies organization, repository, and published snapshot ownership. Requesters cannot supply an organization ID to bypass authentication. `/tests` reports `coverage_claimed: false`.

The signed-in repository page has an Atlas tab for starting indexing, following job status, choosing snapshots, searching symbols, inspecting downstream impact and evidence, and comparing two small snapshots. It needs the same API, PostgreSQL, Redis, repository checkout volume, and worker as other repository features. The UI does not build a graph in the browser or make authorization decisions.

## Validation and operating limits

Apply Alembic migrations before starting updated API and worker images. Both services need the same database, Redis, and repository workspace. Atlas itself does not need a Docker socket; Forge's execution worker still needs a separately hosted Docker-capable environment. No hosted Atlas indexing has been verified. Forge Bench's deterministic fixture is used only for Atlas conformance assertions; its scoring and coding-agent claims are unchanged.

Focused tests cover extraction and provenance, protected paths, pinned revisions, incremental reuse, impact, PostgreSQL snapshot publication, replay, stale recovery, execution-linked Flight Recorder events, RLS, and signed-in cross-tenant API denial. An outbox-to-Redis-to-worker test uses disposable PostgreSQL and Redis. A seeded pre-Atlas upgrade preserved a patch row and its repository, execution, and organization relationships. On the Forge `services/` tree (83 parsed files), one local Linux-container run measured 2,618 ms for scanning, 89 ms for graph construction, and 1,472 ms for a fully reused incremental scan; peak process RSS was 25,220 KiB. A separate read-only scan and graph build of the full current worktree completed in 15.08 seconds with 353 files, 3,744 nodes, 29,220 edges, and no warnings. These are one-run local measurements, not hosted throughput guarantees. Browser interaction tests, hosted indexing, and load tests still require separate validation.
